# Thread Pool Devlog

这份文档记录了我实现这个线程池项目时的设计演进、踩坑过程、问题修复思路，以及我对线程池、条件变量、关闭语义、对象生命周期和测试的理解变化。

我做这个项目时，并不是一开始就把所有问题都想清楚了。很多点是在实现、调试、反复修改和阅读代码的过程中才逐渐理解的。
  这个文档的目的不是包装成“我一开始就会”，而是诚实记录：我最开始哪里不懂，后来是怎么把问题一步步理顺的。

---

## 1. 项目起点

做这个项目的目标主要有两个：

1. 学会用 `pthread`、互斥锁、条件变量实现一个基础线程池
2. 把它整理成一个可以写进简历的 C/C++ 并发项目

一开始我的理解比较偏“先把代码写出来”，对下面这些问题并没有完全搞清楚：

- worker 线程什么时候该睡，什么时候该醒
- 为什么条件变量一定要配合同一把 mutex 使用
- slow shutdown 和 immediate shutdown 的边界到底是什么
- `waitdone()` 到底只是“等待线程结束”，还是“连对象销毁也一起做”
- 指针变量、共享对象、对象生命周期之间的区别是什么

这个项目后面最有价值的部分，其实不是“写出了线程池”，而是我在不断修正这些理解。

## 2. 最初的任务队列设计

线程池内部任务队列使用的是单链表。

核心结构是：

- `head` 指向队首任务
- `tail` 不是尾节点本身，而是“当前尾节点 next 指针的地址”

这个写法一开始我理解得并不顺，但后来发现它有明显好处：

- 入队是 O(1)
- 空队列和非空队列可以统一处理
- 不需要单独分支判断“是不是第一个节点”

也就是说，`tail` 这种“指向 next 指针地址”的写法，虽然刚看不直观，但它能减少很多边界分支。

## 3. 条件变量相关理解的变化

### 3.1 一开始最难理解的点

最开始我不太明白：

- 为什么 worker 线程等待任务时必须写成 `while (...) pthread_cond_wait(...)`
- 为什么不是 `if`
- 为什么“检查条件”和“进入等待”必须和同一把 mutex 绑在一起

后来逐渐理解到：

- `pthread_cond_wait()` 的含义不是“条件满足才返回”
- 它的真正含义更接近于：
- 先释放 mutex
- 当前线程睡眠
- 被唤醒后重新抢回 mutex
- 然后从 `pthread_cond_wait()` 返回

所以线程被唤醒以后，条件不一定真的成立。
这就是必须使用 `while` 的原因，而不能用 `if`。

### 3.2 对“虚假唤醒”和“重新检查条件”的理解

后面我逐渐明白：

- 条件变量的正确用法不是“有人 signal 了，所以条件一定满足”
- 而是“有人 signal 了，所以我有必要重新检查条件”

所以 worker 线程正确的逻辑应该是：

1. 拿锁
2. 检查队列和线程池状态
3. 如果当前不能继续执行，就 wait
4. 被唤醒后重新检查条件
5. 条件满足时再真正取任务

这个理解后面直接影响了我整个 `__get_task()` 的写法。

## 4. 从“先写出来”到真正区分两种关闭语义

项目过程中，一个重要变化是我逐渐明确了线程池关闭其实不是一种，而是两种：

- slow shutdown
- immediate shutdown

### 4.1 slow shutdown

我现在对 slow shutdown 的定义是：

- 停止接收新任务
- 但队列里已经存在的任务要继续执行完
- 当队列清空后，worker 才退出

### 4.2 immediate shutdown

我现在对 immediate shutdown 的定义是：

- 停止接收新任务
- worker 不再取新任务
- 已经在执行中的任务继续执行
- 队列里还没开始执行的任务会被丢弃

这个区别我一开始其实没有完全分清。
尤其是“立即关闭”这个词，最容易误以为是“线程立刻停止”，但真实语义不是这样。
当前实现里，immediate shutdown 不是强杀正在执行的任务，而是“不再开始新任务”。

这也是后面我专门重新设计 shutdown 测试的原因之一。

## 5. 早期实现中的几个关键问题

### 5.1 `waitdone()` 直接调用会卡死

我早期实现里，`threadpool_waitdone()` 只是简单 `join` worker 线程。
这会导致一个问题：

- 如果线程池里没有任务
- worker 线程还在 `pthread_cond_wait()` 里等待
- 主线程直接 `waitdone()`
- worker 没有收到关闭信号
- 主线程就会一直卡在 `join`

后来我才真正理顺：

- `waitdone()` 不能只是“等线程结束”
- 它还必须负责“如果线程池还在运行，就先触发一次优雅关闭”

所以当前版本里，`waitdone()` 的语义变成了：

- 如果线程池还在 `RUNNING`
- 就自动切成 slow shutdown
- 广播唤醒 worker
- 再 `join + destroy`

这一步是我对线程池收尾语义理解的一个重要修正。

### 5.2 持锁 `join` 导致死锁

在一次修改 `waitdone()` 的过程中，我还引入过一个新的问题：

- 主线程拿着 `queue->mutex`
- 还没解锁就去 `pthread_join()`
- worker 退出前又需要进 `__get_task()` 拿同一把锁
- 于是主线程等 worker，worker 等锁
- 直接死锁

这个坑让我真正意识到：

- `join()` 这种等待线程退出的动作，绝不能在持有共享锁的情况下做

所以后来的修正是：

- 状态变更和 `broadcast` 可以在锁内做
- 但 `join()` 必须放到解锁之后

这个问题本身很典型，也让我更清楚地理解了锁的作用范围。

### 5.3 `threadpool_post(NULL func)` 会异步崩溃

早期版本里，`threadpool_post(pool, NULL, arg)` 可能会成功把任务节点放进队列。
问题是 worker 执行时会直接调用空函数指针，导致异步段错误。

后来补上了两个最基本的接口保护：

- `pool == NULL` 时拒绝
- `func == NULL` 时拒绝

这个修改不复杂，但很重要，因为它让错误更早暴露在 API 层，而不是拖到 worker 线程里异步炸掉。

## 6. 一个关键认知变化：状态问题和对象生命周期问题不是一回事

这个项目里，对我帮助最大的一个认识是：

**线程池“当前处于什么状态”和“线程池对象现在能不能被 free”，是两件不同的事。**

我最开始容易把它们混在一起，以为：

- 只要状态变量设计对了
- 销毁问题自然就解决了

后来才发现并不是这样。

### 6.1 `waitdone()` 后外部 `pool` 仍然是悬空指针

当前实现里：

- `threadpool_waitdone(pool)` 最后会 `free(pool)`

这意味着函数返回后：

- 调用者外面的那个 `pool` 变量，仍然保存着旧地址值
- 只是这个地址对应的对象已经不存在了

所以 `waitdone()` 返回后，外部变量里的 `pool` 本身仍然是一个悬空指针。
这件事不是 bug，而是当前 API 设计本身的结果。

### 6.2 我曾误以为 `free(pool); pool = NULL;` 能解决问题

项目过程中，我还犯过一个很典型的误区：

我一度以为在 `threadpool_waitdone()` 最后写：

```c
free(pool);
pool = NULL;
```

就能解决野指针问题。

后来才真正理解：

- pool 是函数自己的局部形参副本
- 把它设成 NULL，只能改当前函数栈上的这一个变量
- 改不了调用者外面的那个变量
- 更改不了别的线程已经持有的旧指针副本

这让我真正理解了：

- 指针变量本身
- 指针的副本
- 指针指向的堆对象

这三者是不同层次的问题。

### 6.3 当前版本采用的是“调用方负责销毁前同步”的模型

我没有继续引入引用计数、句柄分离、正在使用计数等更复杂机制，而是明确保留了一个接口契约：

- 调用 threadpool_waitdone() 前，调用者必须保证不会再有其他线程访问这个 pool

也就是说，当前版本的生命周期模型是：

1. 停止 producer
2. join 所有 producer
3. 调 threadpool_shutdown_slow() 或 threadpool_shutdown_immediately()
4. 调 threadpool_waitdone()

这说明当前项目采用的是“调用方负责销毁前同步”的设计。
对这个项目阶段来说，我认为这是合理的。

## 7. 从两个标志位到单一状态机

早期实现里，我用两个变量表达线程池状态：

- accepting
- stop_now

这种方式虽然可以拼出语义，但后面逐渐暴露出几个问题：

- 代码可读性差
- 判断条件需要脑内翻译
- 容易写出不直观的组合判断
- 理论上存在无意义的组合

后来我把它改成了单一状态机：

- TP_RUNNING
- TP_SHUTDOWN_SLOW
- TP_SHUTDOWN_IMMEDIATE

这个改动的意义不是“修复生命周期问题”，而是：

- 把状态语义说清楚
- 让 post()、__get_task()、shutdown、waitdone() 都围绕同一个状态写
- 消除双变量组合带来的理解成本

我现在对这个改动的认识是：

- 它提升的是“状态表达质量”
- 不是“对象生命周期自动安全”

这两件事必须分开看。

## 8. 测试思路的变化

### 8.1 早期测试的问题

早期测试更多是这种思路：

- 提交很多任务
- 最后比较 posted 和 done

这种测试并不是完全没用，但它太弱了。
因为它测不出来：

- 某些任务重复执行
- 某些任务根本没执行
- shutdown 边界语义是不是准确
- waitdone() 的自动关闭逻辑是否正确

### 8.2 后来为什么要重写测试

后面我逐渐意识到，线程池项目真正值得测的是这些场景：

- 不显式 shutdown，直接 waitdone() 是否能正常退出
- NULL 参数是否被拒绝
- slow shutdown 下任务是否都被执行，而且是恰好一次
- slow shutdown 后是否拒绝新提交
- immediate shutdown 是否真的丢弃了还没开始执行的排队任务
- 多生产者并发提交下，任务是否仍然恰好执行一次

### 8.3 “exact once” 比较总数更强

后来重写测试时，一个很重要的变化是：

- 不再只统计总数
- 而是给每个任务分配唯一 id
- 用 seen[id] 记录每个任务执行次数
- 最后检查每个任务都恰好执行一次

这个改动让我真正理解了：

- “总数对”不等于“语义对”
- 测试不是为了凑个能跑的数字，而是为了验证关键行为

## 9. benchmark 的定位

项目里后来还保留了一个简单 benchmark，用来粗略看吞吐量。

我现在对 benchmark 的理解是：

- 它的作用是粗略观察性能
- 它不能代替 correctness test
- 它更像一个补充说明：线程池不仅能跑，也能做基础吞吐测试

当前 benchmark 的场景比较简单：

- 固定 worker 数量
- 提交大量轻量任务
- 输出总时间和吞吐量

这个层级对当前项目已经够用。

## 11. 当前版本仍然存在的边界和限制

当前版本仍然有明确边界：

- threadpool_waitdone() 前必须保证没有其他线程再访问 pool
- 没有实现引用计数
- 没有实现更严格的对象销毁协议
- 没有 future/promise 风格的任务返回值
- 没有动态扩缩容
- 没有任务优先级队列

这些限制不是简单“忘了做”，而是当前项目范围刻意停在了一个我能解释清楚、也能测试清楚的层级。
